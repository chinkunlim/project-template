# 核心軟體設計準則 (SOLID, DRY, FP/OOP & Atomic Architecture)

> **任務載入時機**：設計模組架構、重構程式邏輯、實作複雜演算法前必讀。

---

## 1. SOLID 原則實戰規範

| 原則 | 本框架落地要求 | ❌ 嚴格禁止的反模式 |
|---|---|---|
| **S — 單一職責** | 每個檔案、類別與函式只有一個修改理由：`entrypoints`（輸入輸出/組裝）、`adapters`（外部I/O/轉DTO）、`services`（純業務邏輯）、`domain`（模型/錯誤）、`config`（設定/環境變數）。 | 在 Adapter 內直接渲染畫面，或在 Service 內直接讀取 `os.environ`。 |
| **O — 開放封閉** | 對擴充開放、對修改封閉。新增資料源、處理策略或供應商時透過註冊表（Registry/Map）或介面擴充，不修改核心調度迴圈。 | 每次新增分支就在主邏輯寫長串 `if / elif / else`。 |
| **L — 里氏替換** | 同一抽象介面的所有實作（如正式版 vs 測試 Mock）必須遵守完全相同的輸入契約、回傳結構與例外標準。 | 某實作失敗回傳 `None`，另一實作卻拋出底層例外，導致呼叫端需寫特例。 |
| **I — 介面隔離** | 函式只接收完成任務所需的**最小參數集合**。純運算函式只傳入必要欄位，不傳入整份大型設定物件。 | 把整份 `config` 傳進單純的字串排版函式。 |
| **D — 依賴反轉** | 核心業務模組（services）不直接依賴底層外部細節，兩者皆依賴抽象介面（以參數注入協作者），確保 100% 離線可測。 | 在業務層頂層直接寫死第三方連線，導致離線無法執行單元測試。 |

---

## 2. DRY 與 SSOT (單一真相來源)

1. **單一設定來源 (SSOT)**：分層架構與品質門檻由 `.agents/project.toml` 定義；執行期設定由 `config` 層讀取，禁止程式碼中散落 Magic Numbers。
2. **禁止複製貼上邏輯**：資料清洗、正規化與錯誤分類邏輯重複出現三次以上時，必須抽取為共用函式。
3. **跨 Agent 入口自動化**：全專案手寫維護 `AGENTS.md`，其餘入口檔由 `python3 scripts/agentctl.py sync` 自動同步。

---

## 3. FP 與 OOP 混合架構

1. **不可變資料傳輸 (DTO)**：跨層傳遞一律使用不可變物件（Python `@dataclass(frozen=True)`、TypeScript `readonly interface`）。
2. **純函式優先 (Pure Functions)**：字串處理、數學計算、格式轉換與邏輯校驗，一律實作為無副作用、相同輸入必得相同輸出的純函式。
3. **物件導向邊界**：僅在需要封裝外部資源連線（連線池、金鑰、Stateful Session）時使用 Class。禁止超過 2 層的深層繼承樹。

## 4. Atomic 原子化原則（函式、狀態、Git）

### 4.1 原子化函式 (Atomic Functions)
- **單一職責**：一個函式只做一件事，保持內部語句在同一抽象層級。
- **量化指標門檻**：
  - 單一函式行數：目標 $\le 40$ 行，超過 80 行擋 commit。
  - 參數個數：目標 $\le 4$ 個，過多時封裝為 DTO。
  - 巢狀層級：目標 $\le 3$ 層，優先使用 Early Return / Guard Clauses。

### 4.2 原子化狀態與成對操作 (Atomic State)
- 具備副作用的狀態變更不可留半套狀態：扣減、預留或交易操作失敗時，必須在錯誤處理中調用對應的補償函式回滾。
- 並發鎖區間最小化：鎖只包住記憶體內部的狀態變更，**嚴禁在持有鎖期間發起外部網路請求**。

### 4.3 原子化提交 (Atomic Commits)
- 每次 Git 提交必須是單一獨立且邏輯完整的單元，提交時程式碼必須 100% 通過離線測試。
